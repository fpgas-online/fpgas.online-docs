# Pulling each repository's documentation into docs.fpgas.online

Date: 2026-10-04. Replaces Phase 5 (tasks 29 to 32) of
[`2026-09-03-docs-port.md`](2026-09-03-docs-port.md).

## The decision

The owner's answer of 2026-10-04 to "where should each area's documentation
live":

> Any documentation specific stuff in the repo should be in that repo (and sync
> / pulled into the docs repo). Anything which is shared across many repos
> should be in the docs repo. Pulling could be done either with sync/copy or
> with submodules.

So the September port's last phase is cancelled. It would have replaced the
source documents in `fpgas.online-test-designs` and `fpgas.online-infra` with
stubs pointing here, which is the opposite direction.

## What it means for this repository

| Kind of page | Lives in | Reaches this site by |
|---|---|---|
| About one repository's own subject: a board's wiring and its test design, what `fpgas-verify` checks, how the gateway is deployed, how the web application works, what a Pi package installs | that repository, under `docs/` | the sync, at a pinned commit |
| About several repositories at once: the landing page, sites, what works and what is planned, the repository list, how to set up a new site, what a site needs from its upstream network, contributing | this repository | being written here |

The pages hand-copied here in September have since been corrected and
restructured, so in most cases this repository's copy is now the better one.
Each such page therefore moves in two steps: first a pull request in the owning
repository brings its document up to this copy, then this repository replaces
its copy with the pulled file. A page is never deleted here before the owning
repository has it.

## Sync or submodules

Sync by copy, as `tools/sync_test_designs.py` already does for the Acorn wiring
sheets. Reasons:

- The docs build needs nothing but this repository, so Read the Docs and the CI
  build cannot fail because another repository is unreachable or moved.
- A change in a source repository arrives as a pull request here, which builds
  with warnings as errors before anyone merges it. A submodule bump would
  arrive the same way, but would bring every file of the source repository
  (test-designs carries bitstream sources and photos) into every docs clone.
- A copy can rewrite links. A document written to be read on GitHub links to
  its neighbours by relative path; pulled into this tree those links must
  either point at another pulled page or become absolute GitHub URLs at the
  pinned commit. A submodule cannot do that.
- `SOURCE` files already record the commit each copy came from.

## Tasks

### 1. Generalise the sync tool

- Rename `tools/sync_test_designs.py` to `tools/sync_sources.py`. Replace `REPO`
  and `FILES` with a manifest, `tools/sources.toml`: one table per
  (repository, source directory, destination directory, file list). A
  repository's default branch is read from GitHub, not assumed to be `main`
  (`tt-commander-app` uses `fpgas-online`).
- Keep the behaviour that makes it safe: exact branch, exact file list, a
  missing file is a loud failure with exit status 2, `--check` writes nothing,
  a new upstream commit alone is not a change.
- Add link rewriting for pulled Markdown: a relative link to a file that is
  also pulled becomes the link to its destination; any other relative link
  becomes `https://github.com/<repo>/blob/<commit>/<path>`. Images that are not
  pulled are a failure, not a rewrite.
- Each pulled page gets a first line Sphinx does not render (a MyST comment)
  naming the repository and path it must be edited in.
- Unit tests for the manifest reader, the change detection and the link
  rewriting, run in the Docs workflow.
- Rename the workflow to `sync-sources.yml`; one pull request per source
  repository, so a break in one does not hold up the others.

### 2. Pilot: one page end to end

`setup/verification.md` from `fpgas.online-test-designs` `docs/verify.md`. The
verify stream asked for exactly this: publish from the repository, not from a
snapshot. It proves the link rewriting on a page with many links.

| `setup/webapp.md` | site `docs/` | welland |

`boards/index.md` and `setup/index.md` stay here: they are the tables of
contents that tie the pulled pages together.

For each row: (a) pull request in the owning repository bringing its document
up to the copy here, reviewed and merged in that repository's queue; (b) add
the file to `tools/sources.toml`; (c) the sync pull request replaces the copy
here; (d) confirm the published page is unchanged apart from intended
corrections.

Site inventory that the September port moved out of test-designs
(`docs/hardware/site-welland.md`, `site-ps1.md`) stays here, in `sites/`; the
test-designs copies are then deleted there by pull request, since a site is
not one repository's subject.

### 4. Finish what Phase 5 was really for

The useful part of Phase 5 was that nothing should point at a stale copy.
After task 3, every README, the landing page at <https://fpgas.online>, the
organisation profile and the site's templates link to docs.fpgas.online for
reading, and to the owning repository for editing.

## Rules that hold throughout

- Site pages carry inventory only; wiring follows the carrier, not the site.
- No page names a host outside the public fleet, or the network upstream of a
  site gateway.
- No counts that drift; measurements carry their date.
- Issues and pull requests go only to repositories under `fpgas-online` and
  `mithro`.
