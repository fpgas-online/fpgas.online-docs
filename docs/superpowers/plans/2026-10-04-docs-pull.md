# Pulling each repository's documentation into docs.fpgas.online

Date: 2026-10-04. Replaces Phase 5 (tasks 29 to 32) of
[`2026-09-03-docs-port.md`](2026-09-03-docs-port.md).

## The decision

The owner's answer of 2026-10-04 to "where should each area's documentation
live":

> Any documentation specific stuff in the repo should be in that repo (and sync
> / pulled into the docs repo). Anything which is shared across many repos
> should be in the docs repo. Pulling could be done either with sync/copy or
> with submodules.

So the September port's last phase is cancelled. It would have replaced the
source documents in `fpgas.online-test-designs` and `fpgas.online-infra` with
stubs pointing here, which is the opposite direction.

## Which pages live where

The rule, including the tiebreak the decision leaves open: **a page lives in a
repository when its subject is that one repository's, so that a change to the
subject is a change to that repository alone. A page whose subject spans two or
more repositories, or a whole site, lives here.**

Applied to every page under `docs/` (outside `superpowers/`, `_static/` and
`boards/acorn/generated/`, which is already pulled):

## Sync by copy, not submodules

Both are allowed by the decision. This plan chooses copy, as
`tools/sync_test_designs.py` already does for the Acorn wiring sheets:

- The docs build needs nothing but this repository. A source repository that
  is unreachable or has moved a file breaks the sync job, loudly, and not the
  published site.
- A document written to be read on GitHub links to its neighbours by relative
  path. Placed in this tree, each link must point at another pulled page or at
  GitHub. A copy rewrites them once; a submodule would need a build-time step
  to do the same, and would put the source tree in the docs tree as it is,
  outside the navigation.
- A change in a source repository arrives as a pull request here, built with
  warnings as errors before it merges. A submodule bump would too.

The cost: one scheduled pull request per source repository whenever its
documents change, and the published page lags the source by up to a day plus
the time that pull request waits.

## Tasks

### 1. Generalise the sync tool

`tools/sync_test_designs.py` becomes `tools/sync_sources.py`, driven by a
manifest `tools/sources.toml`.

- **Manifest, per file.** Each entry is one source file and one destination:
  repository, source path, destination path, and a kind: `page` (a document in
  the navigation), `fragment` (included by a local page, as the Acorn tables
  are) or `asset` (an image). A destination may appear once. A source file may
  appear once. Ownership is per file, not per directory, because `docs/boards/`
  and `docs/setup/` hold pulled and local pages side by side; the tool removes
  a file only if it carries the tool's marker and is no longer in the manifest.
- **Branch.** The repository's default branch, read with
  `git ls-remote --symref <url> HEAD` (no API, no token), never assumed to be
  `main`. The commit copied from is recorded in `tools/sources.lock`, one line
  per repository. A new upstream commit that changes no listed file changes
  nothing here, as today.
- **Marker.** Every pulled Markdown file starts with a MyST comment naming the
  repository and path it must be edited in. The marker has no commit in it, so
  it does not change with every upstream commit.
- **Links in pulled Markdown.** Inline links, reference-style definitions,
  autolinks and raw HTML `<a>`/`<img>`:
  - a relative link to a file that is also pulled becomes the relative link to
    its destination, keeping the `#fragment`;
  - any other relative link becomes
    `https://github.com/<repo>/blob/<default branch>/<path>`. The branch, not
    the commit, so the page does not change with every upstream commit; a file
    that moves upstream shows in the link check;
  - an image that is not in the manifest is a failure, not a rewrite.
- **Checks that fail the sync** (exit status 2, naming the file and line):
  - a listed file missing upstream (as today);
  - a `page` without exactly one top-level heading;
  - a pulled file that contains an `{include}`;
  - a `#fragment` on a link to a pulled page that matches no heading there;
  - a pulled file that names a host on the deny-list in the manifest (the
    network upstream of a site, and private development hosts). The rule that
    no page names them then holds for pulled pages too.
- **Stable destinations.** Local pages link to a pulled page by its
  destination path, which does not change when the source is renamed (the
  manifest entry changes instead). The `-W` build catches a broken one.
- **Tests.** Unit tests for the manifest reader, change detection, link
  rewriting and each check, with no network access, run in the Docs workflow.
- **Workflow.** `sync-test-designs.yml` becomes `sync-sources.yml`: a matrix
  with one job per source repository, each with its own branch
  (`sync/<repository>`), its own `add-paths` computed from the manifest, its
  own concurrency group and its own failure issue. Before the rename, any open
  pull request from `sync/test-designs` is merged or closed, and an open
  "Sync from fpgas.online-test-designs is failing" issue is closed with a
  pointer to the new job.

### 2. Pilot: verification

Pull test-designs `docs/verify.md`, `identity.md` and `verify-goals.md` as
`setup/verification.md` and two neighbours. The page here describes a runner
that no longer exists, so this is a replacement, not a like-for-like swap: the
parts of today's page that are about adding a device to a site move to the
site pages or are dropped, and every link into the old page's headings is
repointed. The verify stream asked for exactly this (publish from the
repository, not from a snapshot), and the document's many links into the
source tree exercise the link rewriting.

### 3. Move the board pages, then publish the two references

For each row of the table above, in this order:

1. A pull request in the owning repository brings its document up to the copy
   here (or writes it, where the state is "none yet"). It is reviewed and
   merged in that repository's queue.
2. The same day it merges, the manifest entry is added here and the sync pull
   request replaces the local copy. Until then the page stays here unchanged,
   and has no manifest entry.
3. The published page is compared with the previous one; only intended
   corrections may differ.

A page is never deleted here before the owning repository has it, and two
copies exist only between steps 1 and 2. Order of rows: Acorn first (it is the
closest to finished and already has the pulled sheets), then Tiny Tapeout FPGA
once its two open corrections merge, then Arty, NeTV2, the Pmod pages, Fomu,
and the boards that are not deployed. `setup/access-reference.md` and
`setup/verify-events.md` need no step 1 and can follow the pilot directly.

### 4. Relink

Last, once the pages are live, so that no link points at a missing page: each
repository's README, the landing page at <https://fpgas.online>
(`fpgas-online.github.io`), the organisation profile (`.github`) and the
site's templates (`fpgas.online-site`) link to docs.fpgas.online for reading
and to the owning repository for editing. Each is a pull request in that
repository's queue.

## Rules that hold throughout

- Site pages carry inventory only; wiring follows the carrier, not the site.
- No page names a host outside the public fleet, or the network upstream of a
  site gateway.
- No counts that drift; measurements carry their date.
- Issues and pull requests go only to repositories under `fpgas-online` and
  `mithro`.
